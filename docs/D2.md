# Software Engineering, Week 2: Development Plan (D2)

**Author:** Eduardo Ion Bocos Varvari
**Project:** UoP Meeting Booking (working title)

## 1. Overview

This document describes how UoP Meeting Booking will be developed: technology choices, repository and issue tracker, initial backlog, milestones, branching strategy, Definition of Done, and the agile practices that will and will not be adopted. The accompanying prototype is available at <https://github.com/bocoseduardo-dot/uop-meeting-booking>.

## 2. Technology choices

The backend is written in Python with FastAPI, persistence uses SQLAlchemy (ORM) over SQLite, tests use pytest, and the web interface is a minimal HTML page that calls the API with JavaScript.

## 3. Repository and issue tracker

The code lives in a GitHub repositoryhttps://github.com/bocoseduardo-dot/uop-meeting-booking. currently private. Its structure is `app/` (backend), `static/` (web page), `tests/` and `docs/` (deliverables and process notes). Issues are tracked with GitHub Issues and a Project board with the columns Backlog, Sprint, In progress and Done. Labels: `feature`, `bug`, `tech`, `docs`.

## 6. Branching strategy

GitHub Flow: `main` always holds working code. Each task is developed on a short-lived branch (`feature/...`, `docs/...`) and merged through a pull request, even as a single developer, so the history stays readable. Branches are deleted after merging, and each milestone is tagged (`v0.1`, ...). [VERIFY: branch protection may be unavailable on a private repository on the free plan.]

## 7. Definition of Done

A task is done when:

1. its acceptance criteria are met;
2. automated tests cover its business rules and pass;
3. it has been reviewed through its pull request (This is basically a self-decision, but in my opinion it should be at least mentioned.);
4. it is merged into `main` with a clear commit message;
5. the README or docs are updated if behaviour changed;
6. no secrets or real personal data are committed;
7. its issue is closed and linked to the pull request.

## 8. Agile practices

Development follows a Scrum adapted to one developer, combined with selected Extreme Programming practices. Sprints last one week: planning on Monday (about 30 minutes, with a sprint goal in one sentence), development from Tuesday to Saturday with tests written along the way, and a written review and retrospective on Sunday at 19:00. Capacity is 8-9 hours per week.

| Practice                     | Decision           | Reason                                                        |
| ---------------------------- | ------------------ | ------------------------------------------------------------- |
| One-week sprint              | Adopted            | Matches the weekly assignments and my Sunday review           |
| Product backlog              | Adopted            | Required, and it records the process                          |
| Planning                     | Adopted, shortened | Items are chosen by capacity                                  |
| Daily scrum                  | Not adopted        | No team to synchronise                                        |
| Review and retrospective     | Adopted, written   | A short note per week gives evidence of the process           |
| Separate PO and Scrum Master | Merged             | One person; the Scrum Master's duties are kept as a checklist |
| Definition of Done           | Adopted            | Nobody else reviews my work                                   |
| User stories                 | Adopted            | They structure the backlog                                    |
| Test-driven development      | Adapted            | Tests for business rules, not for every line                  |
| Continuous integration       | Adopted            | Planned for M2                                                |
| Refactoring                  | Adopted            | In small steps, always protected by tests                     |
| Small releases               | Adopted            | One tagged version per milestone                              |
| Pair programming             | Not adopted        | Single developer; replaced by pull request review             |
| On-site customer             | Adapted            | The professor gives intermittent feedback                     |
