# Software Engineering, Week 6: Architecture Trade-off Analysis (D6)

**Author:** Eduardo Ion Bocos Varvari

**Project:** UoP Meeting Booking

## 1. Context and decision drivers

- **Team:** only one developer. The project should be finished by 20 December, a deadline set by the author, with all tests passing and continuous integration (CI) in place.
- **Expected load:** my estimates for one department are 5-10 professors and 300 students, with at most 100 people arranging meetings on the same day. I expect usage to peak in the first weeks of the year and in the weeks before exams.
- **Quality attributes:** the application must be secure, maintainable and usable for the professors and students of UoP. Performance and scalability are not prioritised: the expected load is small, and since the system is only intended for one department, no large-scale scalability measures are needed.
- **Scope of M2:** M2 completes the project with a login and keeps track of the meetings that a student or professor had, has or will have. It covers the following user stories from D3:
  - **US2:** As a student, I want to see professors' free slots with date, time and location, so that I can choose a meeting without emailing.
  - **US3:** As a student, I want to request a meeting in a free slot, so that I do not have to arrange it by email.
  - **US4:** As a professor, I want to accept or decline meeting requests, so that I only commit to meetings that fit my schedule.
  - **US5:** As a student, I want to see all my meetings with their time, location and status, so that I know where to go and what is confirmed.
  - **US16:** As a user, I want to identify myself with my own account, so that the system can show my meetings and act on my behalf.
- **Critical business rule:** a slot can have at most one active meeting (requested or accepted); with simultaneous requests, the first one wins. This rule is not implemented yet, but D3 marks it as a must for M2, the phase that is now starting. If it fails, we will have two students in the same slot breaking rules such as, only one student per slot and no overlapping slots. To enforce it, checking that the slot is free and creating the meeting must happen in one transaction, with a unique constraint, which is only possible if slots and meetings are in the same database.

## 2. Alternatives

- **Layered monolith:** this is the current implementation. The application is divided into three layers (API, service and data access), and each layer only calls the layer directly below it. The code is organised by technical type, not by functionality. It is one deployable application with a single database.
- **Modular monolith:** the application is divided into modules by domain: slots, meetings and identity, and each module has its own layers inside. At the boundary between modules, a module only uses another through its public functions and never accesses its tables directly. It is still one deployable application with one database, so one request can use a single transaction across several modules, and atomicity is preserved.
- **Microservices:** an implementation where each module of a modular monolith becomes its own deployable service. The services are slots, meetings and identification, and in the future one for notifications. Each service has its own database and is deployed in its own Docker container. The services communicate over the network, with HTTP requests or messages.

## 3. Comparison

| Criterion                            | Layered monolith                                                                                            | Modular monolith                                                                                                | Microservices                                                                                                                                      |
| ------------------------------------ | ----------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| Development effort for one developer | None: it is the current implementation.                                                                     | Low: the existing code only has to be reorganised into modules.                                                 | High: each service needs its own deployment, database and network interface (API contract).                                                        |
| Deployment and operation             | One container and one database to deploy, monitor and back up.                                              | One container and one database, as in the layered monolith.                                                     | One container and one database per service, each to deploy, monitor and back up.                                                                   |
| Consistency of the critical rule     | Guaranteed: one transaction and a unique constraint in one database.                                        | Guaranteed: modules share one database, so one transaction can span them.                                       | Not directly possible: slots and meetings are in different databases, so new coordination logic is needed (distributed locks or sagas).            |
| Scalability                          | Only the whole application can be scaled, and SQLite limits it to a single instance.                        | Same as the layered monolith.                                                                                   | Each service can be scaled independently.                                                                                                          |
| Fault isolation and observability    | A serious failure stops the whole system; errors can be traced in a single log.                             | Same as the layered monolith.                                                                                   | A failure only disables one service, not the whole system; tracing a request across services requires centralised logging and distributed tracing. |
| Maintainability and evolution        | Easy to follow while it is small, but features become mixed as meetings, login and notifications are added. | Clear boundaries: each module has a known public interface, and a module can later be extracted into a service. | Strong boundaries, but every change between services needs coordination over the network.                                                          |

## 4. Decision and justification

Considering the pros and cons of each alternative, microservices are discarded first. They would require a large amount of extra work to make them work as expected, and that cost is not justified: the criteria in which they win (scalability and fault isolation) are not prioritised in this project. Moreover, with microservices the critical business rule could not be guaranteed, because slots and meetings would be in separate databases and could not share one transaction.

The choice is therefore between the layered monolith and the modular monolith. Taking into account the prioritised quality attributes (security, maintainability and usability), both monoliths are equally usable, but the modular monolith makes it easier to keep the system secure, because identification and access checks are contained one module, identity, instead of being spread across all the code, and easier to maintain, because each feature is kept in its own module, so adding meetings and login in M2 will not mix them with the existing code. For these reasons, the modular monolith is selected.

Since only slots are implemented at the moment, migrating to a modular monolith only means reorganising the existing code into modules, each with the same three layers. This decision, refines our first ADR contained in D4.

## 5. Consequences and risks

- **Cost:** organising the code into modules requires a little more effort than keeping the layered monolith, comparing to microservices we lose a bit of scalability but as its not prioritised its not a big deal.
- **Transition:** during the migration, the code will be in an intermediate state, with both organisations (by layers and by modules) living in the same codebase. The transition should therefore be short.
- **Boundary erosion:** if the boundaries between modules are not respected, the modular monolith can degrade into a mixed monolith. Two design rules prevent this:
  1. Only the service that starts a use case commits the transaction. If the slots module committed when called by the meetings module, atomicity would be broken.
  2. Each module owns its tables and never accesses the tables of another module. For example, the meetings module does not query the slots table; it asks the slots module through its public functions.

## 6. When to revisit

- **Larger user base:** the system is extended to other departments or to the whole university.
- **Larger team:** several developers or teams work on the application at the same time.
- **Parts with different needs:** new features that depend on external systems, such as email notifications (US12) or sign-in with the university account (US15), are the first candidates to be extracted as separate services cause they depend of different services.
